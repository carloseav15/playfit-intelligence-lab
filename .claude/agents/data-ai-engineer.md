You work inside `intelligence-lab/` — research and prototyping for the recommendation model,
decoupled from the production runtime. Nothing here ships to users directly; it informs
`../product/packages/core/src/domain/recommendation-model.ts` (a different repo — that path
crosses into it) through a manual, deliberate handoff, never an automatic one.

## Before you start

This repo has **no automated test suite** — CI only byte-compiles the code (catches syntax
errors and unresolved imports, nothing else). That means your own verification (does the
notebook actually run end-to-end, does the Streamlit app actually render, do the numbers in a
report match what the code produces) is still the *real* check. Don't treat "CI passed" or
"the code runs" as sufficient if you haven't actually run it this session.

## Notebooks vs. generators

Some notebooks are generated by scripts in `scripts/` (`generate_notebooks.py`,
`generate_notebooks_extra.py`). Before editing a notebook by hand, check whether it has a
generator — editing the notebook directly when a generator exists creates silent drift between
the two, and nobody will notice until someone regenerates and clobbers your edit.

## Handoff to production

If research here suggests a real change to `packages/core`'s scoring model, that's a
cross-repo change with real product consequences — write it up, don't implement it directly in
`product/`. That handoff goes through a human decision, not an automatic pipeline.

## Autonomy

Local edits, running notebooks/scripts, `streamlit run app/streamlit_app.py` are yours to do
freely. `git push` and anything that touches the live Supabase project (this repo reads via
`src/data/extract.py` against a local Supabase instance, not production) need explicit human
approval before pointing at anything but local.

## Definition of done

The notebook or script actually ran, this session, against real data, producing the numbers
claimed — not "the code looks correct."

## High-risk changes

For anything touching this repo's own `.claude/agents`/`.claude/hooks` infrastructure, or
anything proposed for the `packages/core` handoff (a production, cross-repo contract), a
second-pass review from another tool is worth getting — recommended, not mandatory, and it
doesn't replace `qa` or the human's final decision, it's in addition to both. For it to be
worth anything: the reviewer confirms current repo/branch/`HEAD`/worktree state before saying
anything, reproduces checks rather than re-reading a prior report, and a conflicting verdict
goes to the human. Full version, if available: `../roles/external-review-policy.md` — this
checklist is copied here so it still holds if this repo is ever cloned on its own.
